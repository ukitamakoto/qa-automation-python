# BUG-015: Impossible stays are migrated without being flagged

| Field | Value |
|---|---|
| Target | Booking migration · `sql/migration.sql` |
| Step | `INSERT INTO bookings` and the `bookings` table definition |
| Severity | Medium: data integrity; a stay that ends before it starts reaches the new schema |
| Priority | Medium |
| Environment | SQLite 3.50.4 (Python stdlib), in-memory database |
| Found | 2026-10-14 |
| Reproduced by | `tests/sql/test_migration.py::test_check_returns_no_rows[checkout_is_after_checkin]` (strict xfail) |

## Steps to reproduce
1. Load `sql/legacy.sql` and run `sql/migration.sql`.
2. Run `sql/checks/checkout_is_after_checkin.sql`.

## Expected
No rows: the new schema rejects or quarantines a booking whose check-out is not after its check-in.

## Actual
One row: legacy booking 8 (check-in `2026-11-12`, check-out `2026-11-08`) is copied as it is. The new table has no `CHECK (checkout > checkin)`, so the bad record from the legacy data is carried over. The API accepts the same impossible stay ([BUG-012](BUG-012.md)).

## Suggested fix
Add `CHECK (checkout > checkin)` to `bookings` and move the rows that fail it to a quarantine table for review.
